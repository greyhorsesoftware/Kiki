## Purpose

`kikid` is a long-lived per-user daemon that lists, copies, deletes and mirrors files, keeps a
search index and an access log, brokers `org.freedesktop.FileManager1` and the FileChooser portal
through a helper, and spawns plugin processes for SFTP and FTPS locations and for sharing. The
Quickshell front end is a thin client: it holds a window of rows and a selection, and every action
it takes is a request over `$XDG_RUNTIME_DIR/kiki.sock`. What depends on the daemon, beyond its own
window: any application calling "Show in folder" over D-Bus, any application opening a file chooser
through the portal, the Hyprland keybindings `integrate.rs` writes, and `xdg-open` for
`inode/directory`, `x-scheme-handler/sftp` and `x-scheme-handler/ftps`.

## 1. Security

### Trust boundaries

| Boundary | Parsed by | Bounded by | On malformed input |
|---|---|---|---|
| Unix socket (any process in the user's session) | `proto::Reader` → `kiki_json::parse` | `MAX_JSON_FRAME = 16 * 1024 * 1024`, `MAX_DEPTH: usize = 64` (`crates/kiki-json/src/lib.rs:36`) | `Protocol` error, connection closed |
| Plugin stdout | same reader | 16 MiB JSON, `MAX_BINARY_FRAME = 1024 * 1024` | `"frame too large"` / `"truncated frame"`, reader thread exits, pending requests fail |
| D-Bus `FileManager1` and the portal | `kiki-plugin-dbus` (zbus) → daemon over the same framing | as above | ignored, `{}` reply |
| URIs from other apps | `Uri::parse` → `normalize()` (`kikid/src/vfs/uri.rs`) | scheme charset check, `file://` rejects a host, `..` removed lexically | `UriError` |
| File names on disk | `getdents64` parsed by hand (`vfs/local.rs`) | `d_reclen` from the kernel | names are bytes, `OsString::from_vec`, never re-encoded |

The socket is `0600` both ways — `set_permissions(…from_mode(0o600))` when kikid binds it itself
(`main.rs:35`) and `SocketMode=0600` in `packaging/systemd/kiki.socket` — so the boundary is
"anything running as this user", which is the same privilege the daemon has. Nothing below is a
privilege escalation across users; the findings are about inputs that arrive from *outside* that
set: repositories, archives, remote servers and the session bus.

### 🔴 Browsing a git repository executes commands from its config — **FIXED**

`listing.rs:399` runs git for any local directory inside a repository, with no allow-list:

```rust
if !self.uri.is_local() || !crate::git::enabled() || crate::git::repo_root(&self.path).is_none() {
```

and `git.rs:103` runs

```rust
Command::new("git").args(["-C"]).arg(dir)
    .args(["status", "--porcelain=v2", "-z", "--branch", "--untracked-files=all", "--ignored=matching", "--", "."])
```

git honours the repository's own `.git/config` here, and `core.fsmonitor` is a command git
executes. `safe.directory` does not help: it only refuses repositories owned by *another* user, and
a repository the user downloaded and unpacked is owned by the user.

Verified on this machine (git 2.55.0): a repository with `core.fsmonitor` pointing at a script,
run with kiki's exact flags, executed the script. Unpacking a hostile archive and clicking into the
folder is enough — no file needs to be opened. `git.rs:248` (`git log -1` for the info panel) has
the same exposure.

Verified mitigation: adding `-c core.fsmonitor= -c core.hooksPath=/var/empty` to both invocations
neutralises it. `GIT_OPTIONAL_LOCKS=0` is worth adding at the same time.

**Fixed 2026-09-19.** Every git command now goes through one builder, `git(dir)` in
`kikid/src/git.rs`, which passes both `-c` flags and sets `GIT_OPTIONAL_LOCKS=0`; the two call
sites (`status`, `log -1`) use it and no bare `Command::new("git")` remains outside the tests. A
regression test, `git::tests::a_repository_cannot_run_its_own_config`, builds a repository whose
`core.fsmonitor` and `post-index-change` hook write marker files, runs `status()` through the
production path, and fails if either marker appears — confirmed to fail when the flags are
removed and to pass with them. Measured against real git 2.55.0: `core.fsmonitor` ran and the
hook ran before; neither runs now.

### 🟠 SFTP host keys are trust-on-first-use with no way to pin — **FIXED**

`plugins/kiki-plugin-sftp/src/main.rs:68`:

```rust
async fn check_server_key(&mut self, key: &russh::keys::PublicKey) -> …  {
    Ok(match &self.pinned {
        Some(p) => p == &fp,
        None => true, // trust on first use; the fingerprint is returned to kiki, which pins it in config
    })
}
```

The comment describes something that does not exist. `grep -rn fingerprint kikid/src` returns
nothing, and `grep -rn fingerprint qml/` returns nothing: the daemon never reads the fingerprint out
of the plugin's reply and the shell never shows or stores it. `trustedFingerprint`
(`main.rs:393`) can therefore only ever be set by hand-editing `locations.toml`, so in the shipped
flow every SFTP connection accepts any host key, every time — there is no first-use pin and
`~/.ssh/known_hosts` is not consulted.

FTPS is the counter-example and shows the intended shape: `PinVerifier` (`kiki-plugin-ftps/src/main.rs:75`)
pins when a fingerprint is configured, accepts on an explicit `insecure`, and otherwise falls
through to webpki verification.

**Fixed 2026-09-19.** The key is now shown and has to be accepted before anything is saved:

- `locations::save(location, secrets, trust)` returns `Ok(Some(fingerprint))` instead of saving
  when the plugin reports a key and the location has none pinned. `AddLocation`/`UpdateLocation`
  answer `{ verify, host }`, which is the shell's cue to ask; the shell sends the request again
  with `trust` set to the fingerprint it displayed, and that is written as
  `config.trustedFingerprint`.
- `LocationDialog.qml` shows the fingerprint over a dimmed form, with how to check it against the
  server (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`), and Cancel/Trust-and-save.
- A key that later changes is refused by `check_server_key` and reported as
  `Auth: the host key of <host> has changed — it offered <new>, and this location trusts <old>`
  rather than as a closed connection.
- **`~/.ssh/known_hosts` is consulted** when nothing is pinned yet: a host ssh already knows, with
  the key it records, is accepted and pinned without a second question — the user verified it once
  already — and a host ssh records with a *different* key of the same kind is refused outright,
  naming the line. `KIKI_KNOWN_HOSTS` points the lookup at a fixture for tests.
- Covered by `tests/qml/tst_LocationVerify.qml` (four tests: the key is shown and nothing saved,
  accepting sends `trust` back, refusing saves nothing, a changed key is an error); by the Rust
  contract test, where the stub plugin now offers a fingerprint on `Connect`: saving without trust
  writes nothing and hands the key back, saving with it pins the key, and a pinned location saves
  straight through; and by four tests in `plugins/kiki-plugin-sftp/tests/mock_sftp.rs` against a
  real russh server — known_hosts match, unknown host, known_hosts disagreement, and a pinned key
  that must match.
- Still open: a location saved before this change has no pinned key, so browsing it takes the
  unknown-host path and connects without asking. The next edit of that location pins it.

### 🟡 LocalSend accepts any certificate and checks no fingerprint

`plugins/kiki-plugin-share-localsend/src/http.rs:12` installs an `AcceptAll` verifier, justified in
the file header as "receivers use self-signed certificates identified by fingerprint". The plugin
sends *its own* fingerprint (`main.rs:29`) and compares it only to filter itself out of discovery
(`main.rs:54`); the peer's fingerprint is never compared to anything. The exception is therefore
wider than the comment claims: on a LAN, whatever answers at the discovered address receives the
file. Keeping `AcceptAll` is defensible for LocalSend's model, but the peer fingerprint from the
discovery response should be checked against the certificate before sending bytes.

### 🟡 `restore` takes an unguarded name off the socket

`jobs.rs:497` calls `ops::restore(n.as_str().unwrap_or(""))` with names straight out of the request,
and `ops.rs:225` joins them into paths:

```rust
let info = fs::read_to_string(td.join("info").join(format!("{name}.trashinfo")))?;
…
move_path(&td.join("files").join(name), &orig, &mut p)?;
```

`..` in a name escapes the trash directory in both joins. Every other path into the daemon goes
through `Uri::parse`, whose `normalize()` deletes `..` before anything sees it, which is why the
`trash://` scheme itself is safe (`ops::local_path`) — `restore` is the one path that bypasses it.
Exploitation needs an attacker-placed `.trashinfo`, so this is a missing guard rather than a live
hole; it should reject any name containing `/` or `..`, exactly as the rename handler already does
(`jobs.rs:467`).

### 🟡 Predictable temp paths

- `mirror.rs:900`: `/tmp/kiki-mirror-<pid>-<md5 of the relative path>` opened with
  `std::fs::File::create`, which follows symlinks and truncates.
- `share.rs:137`: `/tmp/kiki-share-<job id>` created with `create_dir_all` — job ids start at 1 —
  then the files being shared are written into it (`share.rs:149`).

`/tmp` is sticky, so another local user cannot remove these, but nothing stops them from creating
the name first: `create_dir_all` succeeds on a directory that already exists whatever its owner, and
the files to be shared are then written where that user can read them. Both should use
`XDG_RUNTIME_DIR` (already `0700`) or create with `O_EXCL` and a random suffix.

### 🔵 Argument injection into `kiki`

`dbus.rs:81`: `Command::new("kiki").arg(first)` where `first` is a URI from any caller on the
session bus. It is argv, not a shell, so this is not command injection — but a URI beginning with
`-` is read as a flag. `--` before the argument closes it.

### Command construction — clean

Every other external command passes user data as argv: `bsdtar` (`archive.rs:51,75`), `udisksctl`
(`config.rs`), `xdg-mime`, `hyprctl`, `secret-tool`, `tailscale`, `kdeconnect-cli`, `signal-cli`,
`opendrop`. The two `sh -c` uses in `openin.rs:205,223` interpolate only values passed through
`shell_quote` (`openin.rs:109`), which is correct POSIX single-quoting, and the substitution order
(`{dir}`, `{files}`, `{file}`, `{uris}`, `{uri}`, `{line}`, `{socket}`, `{prompt}`) means no
placeholder can expand into another. `MirrorWorkspace.qml:123` passes the report text as `$1`
rather than interpolating it — the right pattern.

### Archives — the guard is present

`archive.rs:65` lists members and refuses the whole archive before writing anything:

```rust
if p.is_absolute() || p.components().any(|c| matches!(c, std::path::Component::ParentDir)) {
    return Err(VfsError::Io(format!("refusing unsafe archive entry {}", m.name)));
}
```

plus `--no-same-owner`. Symlink members are handled by libarchive's own secure-extraction defaults
(inference — not tested here).

### Secrets

Secrets reach `secret-tool` on **stdin**, never argv (`locations.rs:84`); `locations.toml` holds
host and username only; `Connect` is the only message carrying them (`locations.rs:151`); nothing
logs them (26 `eprintln!` in the daemon, none with a secret or a user path). The AI integration
stores no keys at all — it runs the provider's own CLI and relies on that tool's login
(`ai.rs:226`).

### `unsafe` and FFI

30 `unsafe` blocks in `kikid`, and `grep -rn SAFETY` across `kikid`, `crates` and `plugins` returns
**2** — so nearly every block is uncommented. Most are `libc` one-liners (`mallopt`, `getuid`,
`localtime_r`, `statvfs`, `poll`, `kill`, `getrusage`). The one that parses a buffer by hand is the
`getdents64` loop (`vfs/local.rs`), which indexes `buf[off + 16..off + 19]` for `d_reclen` and
`d_type` and advances by `reclen`; the values come from the kernel, so the bounds hold, but that
argument exists only in the reader's head. The device plugins (`mtp`, `ptp`, `afc`) hand-write 11
`extern "C"` declarations and are not in the default build — their struct layouts are unverified
here and untested anywhere in CI beyond `cargo build`.

### Findings

| Finding | Evidence | Severity |
|---|---|---|
| ~~One binary-stream slot per plugin, many concurrent streaming requests~~ **FIXED** | `plugin.rs` now holds a `binary: Mutex<()>` gate for the whole of a transfer, taken by `read_stream*` and `write_stream*`; `Scan` streams JSON with its own ids and does not take it, so browsing stays parallel with transfers | ✅ |
| `Plugin::shutdown()` can block forever | `let _ = self.request(… "Shutdown" …); let mut c = self.child.lock().unwrap(); let _ = c.wait();` — no kill, no deadline. The reaper thread calls this (`plugin.rs:361`, called from `start_reaper`), so one plugin that ignores `Shutdown` stops all idle reaping, for plugins, share helpers and service helpers alike | 🟠 |
| Framing duplicated in the SDK with a different bound | `crates/kiki-plugin-sdk/src/lib.rs:305` hard-codes `if len > 16 * 1024 * 1024` for **both** frame types; `proto.rs:12` bounds binary frames at 1 MiB and `API-PLUGIN.md:19` documents 1 MiB. The two ends of the same pipe disagree, and neither imports the other's constant | 🟡 |
| `describe_all()` spawns and shuts down a plugin per uncached scheme on the client thread | `plugin.rs:describe_all` — combined with the `shutdown()` above, a `Plugins` request can hang a client thread | 🟡 |
| `Shell.qml` holds the context-menu model, the keymap dispatcher and the IPC surface | `qml/kiki/Shell.qml`, 945 lines | 🔵 |
| ~~`listing.rs` (1,278) and `mirror.rs` (1,160) are long~~ **FIXED 2026-09-19** | Split along the seams the audit named: `listing/{mod,cache,scan,stats,view,rows,tests}` and `mirror/{mod,filters,detect,diff,scan,execute,report,store,tests}`; the largest file is now 337 lines and behaviour is unchanged (every test green before and after) | ✅ |
| ~~Mirror's temp-file branch documents the single-stream constraint it does not enforce~~ **FIXED** | `mirror.rs:898` "a plugin serves one binary stream at a time, so spool through a temp file" was true per action and not across workers; the gate in `plugin.rs` now makes it true per plugin process, which is what the comment always claimed | ✅ |

**Done well.** Unwrap discipline is genuinely good: excluding tests and `.lock().unwrap()`, there
are about 45 `unwrap`/`expect` calls in the whole daemon, and they sit on `thread::Builder::spawn`,
`child.stdin.take()` after `Stdio::piped()`, and values just proven present. `panic = "abort"`
makes any one of them fatal to the daemon, which is exactly why the count matters. The one that
looked reachable — `path.file_name().unwrap()` in the rename inverse (`jobs.rs:477`) — is safe only
because `Uri::normalize` deletes `..` at the front door; that coupling deserves a comment. Comments
throughout explain *why* rather than what (`listing.rs` on the string pool, `plugin.rs` on the
timeout, `Daemon.qml` on rebuilding the socket through a `Loader`), which is why this audit could
read the code quickly.

### Measured this session (Omarchy, x86_64)

The new `tests/e2e/flows/gallery_perf.py` against 1,000 1600×1200 JPEGs: listing 1,000 files is
1 ms to first rows and 52 ms to the full count daemon-side (~160 ms through the window, including a
22 ms `qs ipc` round trip); a picture decodes in 12 ms average, 21 ms worst, because `sourceSize`
caps every decode at twice the stage; thumbnails are produced at ~338/s cold on four niced workers.
kikid went 5 MB → 26 MB holding the listing. The shell's resident set rises ~62 MB per
1,000-row folder and does not come back — Qt's JS heap and scene graph, not the row objects.

### Allocation discipline

`mallopt(M_MMAP_THRESHOLD, 131072)`, `M_ARENA_MAX 2`, `M_TRIM_THRESHOLD 1 MiB` at start-up
(`main.rs:78`). Buffers are allocated once and reused where the plan says they should be: the
`getdents` buffer per scanner, `COPY_BUF = 1024 * 1024` per copy, the thumbnail decode buffer.
`rss_start_mb: 1.8` versus `rss_listing_mb: 30.9` for 200k entries is a good ratio.

### Timeouts, cancellation and bounds

| Control | State |
|---|---|
| `REQUEST_TIMEOUT` on plugin replies | **present**, 120 s (`plugin.rs:14`) — but see below |
| Cancellation | **present** end to end: `AtomicBool` → `Cancel { target }` → SDK `cancelled()`; scans, jobs, mirror runs and `bsdtar` all check it |
| Listing cache cap | **present**, LRU by entries |
| Journal / access log / index caps | **present** (100 / 50,000 / 10,000) |
| Writer channel to a client | **ABSENT** — `mpsc::channel::<Value>()` (`server.rs:63`) is unbounded. A client that connects, subscribes to job events and stops reading grows the daemon's heap with every event the daemon produces |
| Mirror audit log cap | **ABSENT** — `mirror.rs:audit()` appends to `~/.local/state/kiki/audit.log` forever |
| Thumbnail cache bound | **ABSENT** by design (freedesktop cache, user's `~/.cache`) |
| `bsdtar` deadline | **ABSENT** — `archive.rs:run` checks `cancel` per output line; a bsdtar that produces no output is waited on forever |

The 120 s timeout is weaker than it looks: `wait_reply_with` resets `last_frame` on every frame and
returns only when *both* `last_frame` and `started` exceed the limit, so a plugin that emits one
frame every 119 s holds the calling thread indefinitely. That is the right behaviour for a slow
legitimate transfer and the wrong one for a stuck plugin; there is no total-duration ceiling.

## 4. Maintainability

### Docs versus code

The plans are unusually close to the code — `API-PLUGIN.md:19` states the frame limits the daemon
actually enforces, `API-DAEMON.md` matches the dispatch table arm for arm. Two requests were handled
but not documented: **`Icon`** (`server.rs`, added with the daemon-side icon lookup) and
**`PluginBrowse`** (two arms in `server.rs`, used by `LocationDialog.qml:44`); both are in
`API-DAEMON.md` as of 2026-09-19, along with the `trust`/`verify` fields the host-key flow added.
Everything else that looked like drift was a false positive: `AddLocation`/`UpdateLocation` share
one match arm, and the rest of the "documented but unhandled" list is event names and section
headings.

One plan claim was contradicted by the code: the SFTP plugin's comment that "kiki … pins it in
config" (§1) described a flow no code implemented. The flow now exists, and the comment was
rewritten to describe what actually happens.

### Tests

93 Rust `#[test]` (48 in `kikid`, 27 across the share plugins, 13 in sftp/ftps, 3 in `kiki-json`,
1 SDK loop test), 115 QML tests through `qmltestrunner`, 85 e2e checks over 13 flows under `cage`.
CI runs all three, plus `cargo test --test '*' -- --include-ignored` for the protocol and plugin
contract tests, and the e2e job runs against **the installed package**, not the build tree — the
strongest single thing in this repository's testing.

**Coverage, measured 2026-09-19** (`make coverage`, added with this pass): **62.1% of lines**
across kikid. `server.rs`, `share.rs`, `dbus.rs` and `helpers.rs` read as 0% because only the
e2e flows exercise them, against a daemon that is not instrumented — the figure is a floor. The
split modules run 57–100%, and writing those tests found a sort that never answered when a filter
was active, and a stub plugin that answered a recursive `Scan` out of contract. Both are fixed,
with regression tests. The per-module table is in `docs/0.1.0/11-testing.md`.

Strong example: `plugins/kiki-plugin-sftp/tests/mock_sftp.rs` and the FTPS/SMTP/LocalSend mock
servers drive the real protocol code against a real socket, so the parsing and the session logic are
exercised rather than stubbed. Weak example: `tst_Selection.qml` has a single test function for a
type with anchor, range and toggle semantics; `tst_ViewSwitcher.qml` (2) and `tst_ConfirmDialog.qml`
(2) execute their components more than they interrogate them.

## 5. Operational Readiness

### 🟠 A corrupt config file is silently an empty one, and the next write makes it permanent — **FIXED**

`config.rs:31`:

```rust
Ok(text) => match toml::parse(&text) {
    Ok(v) => v,
    Err(e) => { eprintln!("{}: {e}", path.display()); Value::Obj(BTreeMap::new()) }
}
```

For `settings.toml` that is the right call — defaults are filled in and the app starts. For
`locations.toml` it is data loss: `locations::all()` returns an empty vector, the sidebar shows no
locations, and the moment the user adds one, `upsert` → `write_all(&[new])` rewrites the file with
*only* that entry. The same shape applies to `favorites.toml` (`set_favorites`) and to
`integration.toml`, where the backup of the user's original `mimeapps.list` lives — losing it means
"Remove integration" can no longer restore what it replaced. Writes are atomic (`write_toml` uses a
`.tmp` and `rename`), so the failure mode is a parse error, not a torn file; the fix is to refuse to
write a file that failed to parse rather than to fail fast at start-up.

**Fixed 2026-09-19.** `config::write_toml` re-reads the file it is about to replace and refuses
with `InvalidData` — "`<path>` could not be read; fix or move it, and kiki will write here again" —
when it does not parse. Reading still falls back to the defaults, so the app starts; the error
surfaces through `AddLocation`/`SetFavorites` into the dialog that tried to write.
`config::tests::an_unreadable_file_is_never_overwritten` writes a broken `locations.toml`, proves
it reads as empty, proves the write is refused with the file untouched byte for byte, and proves
that a file that parses (and one that does not exist yet) still writes.

### Startup and failure behaviour

Socket activation is honoured (`LISTEN_PID`/`LISTEN_FDS`, fd 3) and a manual bind is the fallback.
The index thread starts 30 s after boot, so a first run does not compete with the first listing. A
crashed location plugin respawns on next use (`plugin::get` checks `alive()`); a crashed **dbus
helper does not** — `dbus::start()` runs once from `main`, and when its bridge thread ends the
helper is gone until the daemon restarts, taking "Show in folder" and the portal with it. A crashed
shell loses nothing: listings are per-client and dropped on disconnect, jobs and the journal live in
the daemon, and the shell now re-handshakes and reopens (`qml/kiki/Daemon.qml`). Verified
accidentally during this audit: killing the daemon out from under a running shell, then restarting
it, brought the window back on its own.

### Observability

`Ping`, `Version`, `About` (version + build + socket + plugin dir + config dir), `PluginStatus`
(kind, running, path, last `Describe`), `Jobs`/`JobEvents` and the Activity popover cover "is it
alive, what is it running, what did it last say". What is missing for a stuck plugin is elapsed
time per in-flight request — `Plugin::busy()` knows there are pending ids but nothing exposes how
long they have been pending, so "which request is wedged" still needs a debugger. Logging is 26
`eprintln!` lines to the journal with no levels and no verbosity switch; `KIKI_TRACE` exists but
gates exactly one line (`listing.rs:387`). Plugin stderr is inherited, so plugin diagnostics land
in the same journal — good.

### Rollback

`release.yml` builds packages per architecture, publishes a GitHub release with checksums and
pushes `kiki-bin` to the AUR. A bad release rolls back through the pacman cache
(`pacman -U /var/cache/pacman/pkg/kiki-<previous>.pkg.tar.zst`); nothing in the repository
documents that, and `kiki.install` prints no downgrade note.

## 6. Daemon and Plugin Host — Isolation and Protocol Robustness

| Factor | Finding |
|---|---|
| Frame parsing | Caps on both ends, but different: daemon 16 MiB JSON / **1 MiB** binary (`proto.rs:11-12`); SDK **16 MiB for both** (`sdk/src/lib.rs:305`). JSON depth capped at 64 (`kiki-json`). Truncated frame → `UnexpectedEof`, reader thread exits, pending requests fail. A text-framed client can grow the daemon's read buffer to 16 MiB before "line too long" |
| Reply matching | `pending: Mutex<HashMap<u64, Sender<Msg>>>`; a reply with an unknown id is dropped, a duplicate is dropped (the first `remove` wins), a reply that never comes is bounded by `REQUEST_TIMEOUT` **only if the plugin also stops sending other frames** (`wait_reply_with` resets `last_frame` on every frame) |
| Stream discipline | **The weak point.** The daemon keeps one `stream: Mutex<Option<u64>>` per plugin and sets it in `begin()` *before sending*, so the most recently **begun** streaming request owns all incoming binary frames. The SDK serialises `Read`/`Thumb` behind `stream_lock`, so the plugin emits one stream at a time — but the daemon has already moved the slot on |
| Cancellation | Complete: `AtomicBool` polled every 100 ms, `Cancel { target }` sent once, 5 s grace, SDK sets the thread-local flag, handlers poll `cancelled()`, `Cancel` itself is acknowledged (SDK test at `lib.rs:854`) |
| Process lifecycle | Spawn on use, respawn after crash via `alive()`, idle reaper every 60 s with `IDLE_EXIT = 300s`, `Drop` kills the child. `shutdown()` waits on the child with no deadline — one unresponsive plugin stops the reaper permanently |
| Concurrency | SDK `MAX_CONCURRENT: usize = 8` with a condvar gate; sessions behind their own mutexes; `tokio` current-thread in the plugins that need it |
| Resource bounds | Listing cache 500k entries, journal 100, access log compacted at 50k, index 10k results — all present. Writer channel to a client and the mirror audit log are unbounded |
| Failure reporting | Typed codes survive the whole way: plugin `err.code` → `VfsError` (`plugin.rs:finish`) → `proto::err` → shell toast. `NotFound`, `Denied`/`Auth`, `Exists`, `NotEmpty`, `Unsupported` map explicitly; everything else becomes `Io` with the original code prefixed into the message |

### Fixed 2026-09-19: the stream slot

`Plugin` gained `binary: Mutex<()>`, held from the request going out to the final reply by
`read_stream`/`read_stream_with` (a reply that streams binary frames) and by
`write_stream`/`write_stream_with` (binary frames going the other way, which the SDK routes to
the single `Write` it has in flight). `Scan` keeps `request_stream*`, which does not take the
gate and no longer touches the `stream` slot at all — its frames are JSON and carry their own
ids — so listing a location while a transfer runs is still parallel. The four `Read` call sites
in `mirror.rs` and `share.rs` were moved onto the gated method.

Proved by `stub_plugin_end_to_end`: the stub gained a `slow.bin` that streams over ~180 ms, and
the test starts a second `Read` 40 ms into it. With the gate, each read gets its own bytes
(3,072 bytes of `7`, and `hello`). Without it the test fails with `left: 0, right: 3072` — the
slow read receives nothing at all, because its frames were delivered to the other request.

### Verdict

**A misbehaving plugin cannot crash the daemon, but it can wedge parts of it.** Frames are bounded
and typed, a dead plugin fails its pending requests, and a crashed one respawns. But a plugin that
emits any frame more often than every 120 s holds its caller's thread for as long as it likes, and a
plugin that ignores `Shutdown` blocks the reaper thread forever — after which no plugin, share
helper or service helper is ever reaped again.

**A misbehaving shell client can grow the daemon without bound.** The per-client writer channel is
unbounded, so a client that subscribes and stops reading turns every event into heap.

**The one correctness bug in the protocol layer was the stream slot** (fixed; the paragraph below
is the diagnosis as written). A mirror run with the default
three workers issues three concurrent `Read`s to one plugin process; each sets
`stream = Some(its own id)` before the previous one has finished streaming. The frames of the
request the plugin is actually serving are delivered to the channel of the most recently begun one,
and when the first finishes it clears the slot, discarding the rest. The consequences range from a
zero-length file at the destination to one file's bytes written to another's path; the mirror does
not verify the `{ bytes }` the plugin reports against `a.bytes`, so nothing notices until the next
scan. The remote→remote branch on a single plugin already spools through a temp file "because a
plugin serves one binary stream at a time" (`mirror.rs:898`) — the invariant is understood, but it
is enforced per action rather than per plugin process. The fix is a per-plugin streaming mutex held
from `begin()` to the final reply, or routing binary frames by the id the plugin echoes.

*(Inference: I did not build a two-stream reproduction — the reasoning is from the code path, which
is unambiguous about when the slot is set and cleared.)*
